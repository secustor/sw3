# Prior art: adding ships to Star Wolves 3: Civil War

Scope: what other modders have done to add hulls (carcasses) to SW3 (and the same engine in SW2 / SW2:GV), split into (a) data-only ships that reuse an existing mesh and (b) ships with new or modified IMD models and textures. Covers files touched, tools, engine limits and save behaviour reported by the community.

Citation conventions:
- Web pages were saved as text under `.work/ships/dl/` (paths below are relative to `/Users/secustor/repos/secustor/sw3/`). A citation like `dl/web/t13859.txt:170` points at the line in that saved copy; the source URL is in the Sources list (letters in brackets).
- `GOG:` paths are under `/Users/secustor/Games/Heroic/Star Wolves 3 - Civil War/`. Addresses are GOG `sw3cw.exe` VAs, checked in `.work/exe.asm`.
- "verified locally" means I checked it against the GOG 1.12 files. UNVERIFIED marks forum claims nobody has confirmed and my own inferences.
- Forum archive pages repeat quoted text, so one statement can show up on two lines. I cite the first one.

## 1. Short answer

1. **Data-only ships work and have been done many times since 2010.** You copy a `Carcasses.xml` entry, give it a unique `name`, point `mesh_name`/`flat_image`/`mapping_name` at existing assets, add loc strings, and register the ship in a shop script or spawn it from Lua. Sources: dl/web/t13859.txt:105-164 [A], dl/web/g761154053.txt:107-181, 207-252 [F], dl/web/g891596223.txt:9-26 [G], dl/web/eg49483.txt:172-188 [H].
2. **New meshes have also been shipped.** Examples: SW1/SW2 ports (dl/web/t13859.txt:193 [A]), edited or new IMDs from Goblin Wizard and Nanaki (dl/web/t13859.txt:259, 292-301 [A]), ALEX DART's eight hulls on Elite Games (dl/web/eg54738.txt:70-277 [I]; critic correction, was "six"), SW3EXP's EVE ships built in 3ds Max (dl/web/t229453.txt:84-88, 148-151 [J]), NCW's ships taken from X, Galaxy on Fire 2 and EVE (dl/web/g766483986.txt:45-50 [K]), and the Stone Arrow Remaster from 2025 with a new mesh and 2K textures (dl/web/eg54738_60.txt:205-227 [I]). Weapon hardpoints, hangars and engine flares live inside the IMD as `GREF` reference points. GUI slots live in a separate `TEXTURE/Interface/Carcass/Slots/<mapping_name>.ini` that must match the IMD reference names (dl/web/t13859.txt:442 [A]). I verified that link locally, see section 4.
3. **Every released content mod overwrites `Data/` files.** That includes the merge-by-hand `Carcasses.xml` snippets: dl/web/eg54738.txt:76 [I], dl/sa/README.txt:10-14 [L]. The only route that adds ships without overwriting files is SW3SE's runtime XML loader (section 3.1). Its shipped example `Carcasses.xml` is empty (dl/sw3se/ex/redist_Data_mods_examplemod_game_Carcasses.xml.txt:1-4 [M]), so nobody has shown a new ship end to end through it. UNVERIFIED.
4. **Tools exist, all of them old or partial:**
   - Tech's IMDeditor v3 (2007): OBJ import/export and reference editing, no GK weapon types.
   - An official 3ds Max 8 / 2008 IMD export plugin from xBow / Elite Games, distributed by the community.
   - IMDeditor v2.
   - SW3SE's MIT-licensed Blender 4.2 importer and exporter plus a Kaitai spec (2025).
   - SWX.SLOTMark (slot .ini editor) and SWX.TUVMark (.tuv editor).
   - "SW Editor by Star Rover Team", linked as an alternative to IMDeditor (dl/web/g761154053.txt:172). Added by critic, not inspected.

   The developers' internal editor will "never" be released (dl/web/eg49483.txt:334 [H]).

## 3. What the prior art proves, by case

### 3.1 Case (a): data-only ship reusing an existing mesh

Minimum file set, agreed across [A], [F], [G], [H]:
1. `Data/Game/Carcasses.xml`: copy an entry of the right class and give it a unique `name`. Classes in GOG: `Interceptor` 201, `BigShip` 154, `SpaceCarcass` 155, `Station` 134, `TradeStation` 15, `Corvette` 12, `Portal` 9 (verified locally). Key fields: `mesh_name` (IMD in `Data/OBJECT`), `flat_image` (DDS in `TEXTURE/Interface/Carcass/32|64|128`), `mapping_name` (slot INI in `TEXTURE/Interface/Carcass/Slots`; the slot picture is not per ship, see Critic additions C2), `HolderProperties` slot counts, `destroyed_mesh_name`, `BigShipHangar` (dl/web/g761154053.txt:107-152). The engine reads these tag names as literal strings (verified locally: `HolderProperties` 0x73da08, `big_guns` 0x73da1c, `gk_turrets` 0x73da4c, `hangar_count` 0x73d81c, `destroyed_mesh_name` 0x73d584, `flat_image` 0x73bcbc, `mapping_name` 0x728530).
2. `Data/LocData/<lang>/m_carcasses.loc` (player ships) or `s_carcasses.loc` (NPC ships) for `#M_Name_*` and similar keys. A missing key shows `Not found string: ...` in game (dl/web/g761154053.txt:178). Edits to existing keys only show after the object is re-created (dl/web/t13859.txt:354).
3. `Data/Game/ShipDescriptions.xml` for pre-equipped variants (`<ShipDescription name=..><carcass>..</carcass><module>..</module>`) used by NPC spawns and quest grants (dl/web/t13859p2.txt:266-276; dl/web/eg49483.txt:391). GOG has 579 entries (verified locally).
4. Spawning:
   - In a shop: `__All_ships` in `include/FloodTradeStations.script` plus the `NShop_*` tables in `InitTradeSystem.script` (dl/web/t13859.txt:152-164), or `GetWhiteMarket/GetBlackMarket(shop):ShipGoodsState(...)` at the end of `InitTradeSystem.script` (dl/web/g761154053.txt:226-239). Both take effect only on a new game (dl/web/g761154053.txt:240; dl/web/t13859.txt:164).
   - In the player's hold: `mothership:AddShipToInventory(name, n)`, which also works from the console as `runscript` (dl/web/g761154053.txt:213-224).
   - In NPC flights: edit the flight tables in `include/Create_flight_2.script` (dl/web/g761154053.txt:241-252).
   - As a mothership: `NewFlight` + `SetPlayerMotherShip` (dl/web/t13859.txt:397-403). `NewFlight` is Lua (GOG:Data/Scripts/include/Create_flight_2.script:30); `SetPlayerMotherShip` is used by vanilla quests (GOG:Data/Scripts/Quests/mission_13a/SavingFriend_a_XT24.script:718).
5. Slot changes that need no IMD edit: system slots only (dl/web/g891596223.txt:25-26; dl/web/t13859p2.txt:209). Big guns and missiles are interchangeable on the same hardpoint. Small guns and turrets are not (dl/web/t13859.txt:172; dl/web/t13859p2.txt:66).

Reported pitfalls:
- Swapping `mesh_name` changes handling: a trailer given the Stone Arrow mesh dropped from maneuverability 40 to 8. The explanation given was "size affects maneuverability, so does mass" (dl/web/eg49483.txt:452, 478). UNVERIFIED mechanism.
- Slot INI files load once per exe start (dl/web/g761154053.txt:202; dl/web/sd_slots3.txt:89).
- Changed stats on an existing ship apply only after it is re-created: change location, or load a save from before it spawned (dl/web/g761154053.txt:204; dl/web/t13859.txt:354; dl/web/sd_slots3.txt:99).
- Object names must not collide with any other Game XML name (`ac2` vs `AC2`, row 8).

### 3.2 Case (b): new or modified mesh and textures

- Pipeline used in practice: model in any tool, then OBJ, then IMDeditor v3 (import, then add references), or model in 3ds Max 2008 with the xBow IMD exporter. Then DDS textures (DXT3/DXT5 with alpha, mipmaps on model textures) in `Data/TEXTURE`, the IMD in `Data/OBJECT`, a slot INI in `Slots` whose `[image]` section points at a 512x340 cell of a 1024x1024 atlas sheet (Critic additions C2; the guide's "1024x1024 DDS" at dl/web/g761154053.txt:179 is the sheet), and icons in `Carcass/32|64|128` (dl/web/g761154053.txt:30-40, 169-181; dl/web/eg49483.txt:95-156; dl/web/t229453.txt:148-151).
- Hardpoints: each weapon, turret, GK and hangar point is an IMD reference. Its name must be unique and must equal the `refpoint=` in the slot INI (dl/web/t13859.txt:442). Hangars need `HangarIn` / `HangarOut` references (dl/web/t13859p2.txt:732). Fighter docking depends on collision spheres, hangar position and docking vectors (dl/web/t13859p3.txt:39). Coordinates are placed by trial and error (dl/web/t13859.txt:279).
- Textures: SW2 textures load in SW3 (dl/web/t13859.txt:200). GIMP of that time could not show SW3 DDS correctly (dl/web/t13859.txt:227). Photoshop was used (dl/web/t13859.txt:304-311); the guide links the NVIDIA DDS plugin (dl/web/g761154053.txt:174).
- Known failure modes:
  - The model cannot be selected or hit until the collision and bounds are fixed (row 8).
  - New-mesh collision blocks turret fire (row 7).
  - A crash when a ported ship appears in a shop (row 1).
  - A crash with "LOGfile.txt is complaining can't load textures" (dl/web/t13859p2.txt:127). The poster had several mods and an older save and guessed at the cause, so the link to missing textures is UNVERIFIED.

## 4. Local verification of the IMD to slot-INI link

Script: `.work/ships/scripts/imd_refs.py` (reads the GREF block per SW3SE's KSY layout).
- `GOG:Data/OBJECT/Bident_player.IMD`: header `LIBF ... IDFM GNFO` (xxd offset 0). Blocks present: GBND, GELP, GMAT, GNFO, GNIN, GREF, GVTX. GREF has 92 references: `Rockets:left|left_up|right|right_up`, `Smallgun:LeftSG|RightSG`, 6 `Fire:` and 80 `Flare:`. The slot file `GOG:Data/TEXTURE/Interface/Carcass/Slots/bident_shop.ini` uses `refpoint=LeftSG`, `RightSG`, `left_up`, `right_up`, `left`, `right` for SmallGun/RocketModule, and `system1`, `system2` for SystemModule, which have no GREF entry. This matches the forum rule that system slots need no IMD edit.
- `Lion_Cruiser_MK2_A_grey.IMD`: `GKGun:Front_Down|Front_Up`, `Turret:down_front|left|right|up_back`, `HangarIn:`, `HangarOut:Dispatcher:MshipDispatcher_lion`, 11 `TractorBeam:`.
- All 988 IMDs in `GOG:Data/OBJECT` that contain GREF parse exactly to EOF with the KSY record layout (4 + name + 48 + 16 + 12 + 4 bytes), 0 mismatches. `Data/OBJECT` holds 990 files, all `.IMD`/`.imd`.
- `GOG:Data/XMLSchema/*.xsd` exists on disk (for example `Carcasses.xsd` lists `Interceptor` and `Corvette`). The exe contains no `xs:element`, `.xsd` or `XMLSchema` strings, ASCII or UTF-16. So the forum claim that the game validates against "its own internal hardcoded XML Schema" (dl/web/t13859.txt:407) does not mean an embedded XSD text. The claimed hard-coding is more likely the class registry. UNVERIFIED.

## 6. What remains unknown

1. Whether a save stores carcass instances by template name, by copied stats, or both. Forum behaviour (stats refresh only after re-creation) suggests copied stats plus the name. UNVERIFIED. Also what happens when a save names a carcass that is no longer in any XML (mod uninstalled). Nobody reports testing this. Critic: answered statically in the sibling note `.work/ships/engine.md:12, 176-182`: the save holds class id, every reflected property value and the lower-cased template name; GameObject::Save 0x4a3d00 / Load 0x4a3d70 exist at `.work/exe.asm` lines 215416, 215465 (rest of that analysis not re-checked here).
2. Whether SW3SE's CreateObject fallback covers every lookup a new carcass needs. That means shop listing, slot INI via `mapping_name`, `ShipDescriptions` `<carcass>`, the hangar, and save reload. No public example adds a carcass this way (row 14).
3. Whether the engine accepts unknown tags in `Carcasses.xml` silently. NCW implies yes (UNVERIFIED), and it matters for any mod-side metadata. Critic: `.work/ships/engine.md:11` reports that each class reads a fixed list of reflected properties, every one must be present or the spawn fails, and extra child elements are not read (loop static, absence of other scans inferred).
4. Why some new meshes are not hittable or selectable until fixed. The likely cause is GBND/GELP bounds or the main bounding sphere (the SW3SE exporter writes the largest sphere as the main GBND, dl/sw3se/imd_exporter.py.txt:395-417). UNVERIFIED.
5. Where `HangarOut:Dispatcher:<name>` dispatchers are defined, and whether a new hangar mesh needs a new dispatcher. Critic: resolved. They are Lua functions `MSHIPDISPATCHER`, `_ARBA`, `_LION`, `_WELL`, `_KFNI`, `_CORP` (GOG:Data/Scripts/AI/mshipHangarDispatcher.script:7-28, verified), loaded from GOG:Data/Scripts/system.lst:13. The author's grep probably missed them because the file is ISO-8859 and grep stopped on the encoding. A new carrier mesh can name an existing dispatcher or needs a new Lua function (`.work/ships/scripts.md:164-166`, `.work/ships/data-format.md:184`).
6. Whether the SW3SE Blender exporter produces IMDs the game accepts. No in-game report found. Critic: the missing GNIN chunk is harmless: 362 of 990 vanilla IMDs have no GNIN (628 have it, `grep -a GNIN`), and the IMD loader vtable 0x717dc0 has slot +0x18 = 0x5ac3c0, which is `movl $0x1,%eax; retl $0x4` (`.work/exe.asm` line 566031, verified).
7. Real GUI slot limits (24, or the 2 GK / 5 turret reports) and whether they are exe constants.
8. Archive contents of SW3EXP, NCW, Motherships Mod and the EG ship packs. Only names and sizes were visible. I downloaded nothing executable and no archives.

## Critic additions

Re-opened 47 citations (forum lines, guide lines, GOG files, exe strings and asm lines, SW3SE sources, one URL). Corrections are marked inline. Items below were missing for "what would it take to add a ship".

- C1. The XMLSchema finding in section 4 re-checks: 0 hits for `xs:element`, `.xsd`, `XMLSchema` in sw3cw.exe in ASCII and UTF-16; `Carcasses.xsd` names the 7 classes plus the root. `.work/ships/engine.md:10` states the class tags are C++ class names from a registry, so new element kinds are impossible without native code. The "class registry" inference in section 4 is consistent with that note.
- C2. Slot pictures are an atlas, not one DDS per ship. All 60 slot INIs in GOG:Data/TEXTURE/Interface/Carcass/Slots have an `[image]` block with `name=shipsNN`, `tuv=ships`, `index=0..5` (example: bident_shop.ini lines 1-4: `name=ships02`, `tuv=ships`, `index=0`). `ships.tuv` declares `TUVCOUNT 6`, `TUVBASE 1024 1024` and six 512x340 cells. The folder holds 12 sheets (`ships01`..`ships11`, `ships01_alien`), all 1024x1024. So a new ship needs either a free or reused cell in an existing sheet (which overwrites a vanilla file) or a new sheet with a new name, which is what ALEX DART's `ships99` is (dl/web/eg54738.txt:215). Whether a sheet can use another .tuv is UNVERIFIED.
- C3. Coverage of vanilla data: 680 entries in Carcasses.xml; 367 (all Interceptor, BigShip, Corvette) have `mapping_name`, and every one has a matching INI; every `mesh_name` except `Planet` has an IMD in Data/OBJECT. No duplicate name inside Carcasses.xml. Vanilla slot INIs have 7 to 12 `[slotN]` sections, far below the reported 24 GUI limit and the ~135-slot SW3EXP Hurricane INI ([P]).
- C4. Lua side of spawning: `NewFlight` is a Lua function (GOG:Data/Scripts/include/Create_flight_2.script:30); `SetPlayerMotherShip`, `AddShipToInventory`, `ShipGoodsState`, `CreateCarcass` are exe strings (native). `__All_ships` is at GOG:Data/Scripts/include/FloodTradeStations.script:177; vanilla `ShipGoodsState` calls start at GOG:Data/Scripts/InitTradeSystem.script:501. The guide's `AddShipToInventory` example goes into `InitTeamScript.script` after the mothership is created (dl/web/g761154053.txt:213-219), which also runs only on a new game (mods/traffic/design/mod-research/community-prior-art.md:75).
- C5. Handling depends on more than the XML value: the same EG reply says steering power affects turning and that `maneurability` has no effect at all (dl/web/eg49483.txt:478). UNVERIFIED, but it matters when tuning a data-only ship.
- C6. Sibling notes in `.work/ships/` already answer several of section 6's open points (save content, unknown tags, dispatchers, GNIN). The prior-art note did not cross-reference them; links were added inline above.
- C7. Still open, not covered by any prior art seen: whether `destroyed_mesh_name` and the `explosion_script` must exist for a new hull, how the engine picks the 32/64/128 icons from `flat_image`, and any limit on the number of carcass templates. Not checked by the critic.
