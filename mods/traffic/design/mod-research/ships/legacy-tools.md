# IMD and asset tools other than SW3SE

Scope: every tool besides SW3SE that reads or writes Star Wolves IMD meshes or the ship GUI files, which game it targets, which format version it handles, where a copy still exists, whether it can run on this Mac, and what it proves for adding SW3 ships.

Conventions:
- `LT/` is `/Users/secustor/repos/secustor/sw3/.work/ships2/legacy-tools/`. Downloads are in `LT/dl/` and were never executed. Scripts are in `LT/scripts/`, run with `python3 -I` (Python 3.12.15). Their outputs are in `LT/scripts/*.out` and `LT/scripts/*.asm`.
- `OLD/` is `/Users/secustor/repos/secustor/sw3/.work/ships/dl/web/` (pages saved by the earlier research).
- `GOG:` is `/Users/secustor/Games/Heroic/Star Wolves 3 - Civil War/`.
- Addresses such as `0x401843` are VAs inside the named tool binary, taken from `objdump -d` listings in `LT/scripts/`.
- Naming: the Russian community calls SW3: Civil War "ЗВ2ГВ" ("Звёздные волки 2: Гражданская война", 2009). Russian threads that say "for SW2:GV" mean the game we mod. Source: ru.wikipedia search summary (https://ru.wikipedia.org/wiki/Звёздные_волки). This also explains why the EG tools thread sits in the "Звездные волки 2: Гражданская война" forum (LT/dl/web/eg51964.txt:20).

## 1. Summary

1. All Star Wolves IMDs inspected use the same container. SW3 files have `u32 100` in every GNFO, GVTX, GMAT and GREF chunk (990 files, `LT/scripts/vanilla_refs.out`). Four IMDs that are not in SW3 (probably SW2 [Critic: or SW1, see 3.3]; Raven, Mataris, MegaStation, AngorFighter) have the same `LIBF … IDFM GNFO` header, `100`, six zeros and `1.0` (`LT/scripts/sw2_headers.out`). No tool checks the `100`: IMDeditor and krink's MAXScript importer only check the `LIBF` magic (IMDeditor `0x4017e8`; MAXScript importer `LT/docs/krink_imd_importer_2010.ms.txt:387-389`). [Critic: the citation is for the MAXScript, not for the Xbow `objimp.dli` importer; the DLL's check was not traced (UNVERIFIED).] SW1 files were not knowingly inspected (UNVERIFIED). [Critic: GBND (989), GELP (357) and GNIN (628) chunks also all carry `100` (`.work/ships2/legacy-tools-critic/chunk_versions.out`).]
2. **The official Xbow 3ds Max 8 plugin still exists and was downloaded.** It contains an IMD exporter (`MyExpPlg.dle`) and an IMD importer (`objimp.dli`). It is a 2006 debug build for 3ds Max 8 only (`LibVersion` returns `0x1f401100` = Max release 8000, API 17). The "3ds Max 2008 exporter" that SW3EXP used is byte-identical to it (same SHA-256). Running it needs a licensed 3ds Max 8 install. That is not practical on this Mac. As a format reference, it shows that the developers' exporter writes LIBF, IDFM, GNFO with `100`, GMAT, GVTX, GREF, GBND and GELP, and never writes GNIN. [Critic: the exporter also compares Max node names with `"GBND"` and `"GELP"` (`0x1001202e`, `0x10012081`), so collision spheres and the ellipse are taken from scene objects with those names; krink's importer creates hidden Sphere objects named `GBND`/`GELP` (`LT/docs/krink_imd_importer_2010.ms.txt:512-524`). Inferred from the compares, UNVERIFIED.]
3. **IMDeditor v3 by Tech (2007) and v2 (2006) were downloaded.** Both are 32-bit Borland C++Builder GUI programs that import only standard Win32 DLLs. They should run under the Wine build Heroic ships (UNVERIFIED, not run). From the code, v3 refuses IMDs with more than 100 submeshes or 100 materials and GREF blocks with more than 1000 references. Of the 990 vanilla SW3 IMDs, only `ModuleStation_vks.IMD` (239 submeshes) exceeds a limit. IMDeditor has no `GKGun`/`TurretGK` reference type, but vanilla SW3 uses 54 `GKGun` and 10 `TurretGK` references. ~~On save it does not write GNIN~~ [Critic correction: wrong. The save routine writes the GNIN buffer (`0x403314`-`0x403378`, fwrite `0x476d7c` of tag `0x4a88dc`, size, version, count and `6n` u16) when the flag byte `0x4953fc` is set; load sets it at `0x4022e5` after reading a GNIN. Only the OBJ import path clears it (`0x40a39b`). So an open/save of a vanilla IMD keeps GNIN; an OBJ import produces an IMD without GNIN, which SW3 ignores anyway.]
4. **A 2010 MAXScript IMD importer by krink (Michael Papurin)** is published in full in an Elite Games thread. I extracted it as text. It is the only other readable source for the format. Its GMAT field names differ from our parser's (section 4). [Critic: they are the same names SW3SE's ksy uses.]
5. Nothing else exists, as far as the searches reached. I found no Noesis plugin, Ninja Ripper profile, Kaitai spec other than SW3SE's, or Blender add-on other than SW3SE's. TrID knows the format by signature only. "SW Editor" by the Star Rover team exists as `SWEditor.7z` on VK, behind a login and JavaScript download. I could not fetch it.
6. Verdict for the ship pipeline: SW3SE (Blender) stays the only writer that runs without a dead commercial host. IMDeditor v3 under Wine is a usable second tool for adding and moving refpoints, for OBJ to IMD round trips and as an independent check of exported files (UNVERIFIED until it is run; see Critic additions for what its OBJ import regenerates). The Xbow plugin and krink's script serve as format references.

## 3. What each tool proves, with evidence

### 3.1 Xbow 3ds Max 8 plugin

- Identity: `objimp.dli` is built from the Autodesk SDK OBJ importer sample. Its version resource still says "Wavefront OBJ file importer (plugin)", 8.0.0.92, "TECH: don.brittain" (`LT/scripts/objimp_resources.out:4`). Krink rewrote it to read IMD: its string table names "Xbow Software IMD file importer" and "Krink", and its `.rdata` holds `LIBF GVTX GMAT GREF GBND GELP` (`LT/scripts/pe_inspect_plugin.out:35`; `LT/scripts/rdata_strings_objimp.dli.out`).
- Host: both DLLs export `LibVersion` → `mov eax, 0x1f401100`. That decodes to MAX_RELEASE 8000, API 17, SDK 0, so the host is 3ds Max 8. Both are debug builds that need `MSVCR70D`/`MSVCP70D`/`MSVCI70D`, which ship in the rar.
- SW3EXP's claim of "3DS MAX 2008 Plugin *.IMD Exporter by xBow Software and Elite Games Team" (OLD/t229453.txt:149-151) points at this same Max 8 build: the mega file is named `3dsMax8_SW3_IMD_Plugin.rar` and its bytes are identical. How nocalora loaded a Max 8 plugin into Max 2008 is unexplained (UNVERIFIED).
- What the exporter writes, read from the disassembly at `0x10015ab3`-`0x10015be1` (`LT/scripts/MyExpPlg.asm:8870-8962`; the `1.0f` write starts at `0x10015bd4`, line 8956):
  1. `"LIBF"`, then a 4-byte placeholder for the size.
  2. `"IDFMGNFO"`, then a 4-byte placeholder.
  3. `100`, then six 4-byte zeros (loop to 6), then `1.0f`.

  This matches the vanilla GNFO header in `mods/traffic/design/mod-research/ships/assets.md:57-59` exactly. Its class `Version()` returns `100` (`0x100151d3`). `GBND` and `GELP` appear in two code paths each, `GREF` in two, and there is no `GNIN` anywhere in the file. [Critic: `GBND`/`GELP` have three references each: a node-name compare (`MyExpPlg.asm:2259`, `:2283`), a write (`:9544`, `:9724`) and a chunk-object constructor (`:13101`, `:13441`). `GMAT`, `GVTX`, `GREF` have two (write and constructor).] 362 of 990 vanilla meshes have no GNIN either (`ships/prior-art.md:111`). Inference (UNVERIFIED): those meshes came out of this exporter, so an SW3-loadable IMD without GNIN is the developers' own output shape.
- Reported defects: flares break on re-export (OLD/t13859p2.txt:2096), and 3ds Max "doesn't like exporting models with working Flares/Blinking Lights" (:2330).

### 3.2 IMDeditor v2 / v3

- Build: Borland C++Builder (exports `@@Unit1@Initialize`, `_Form1`, `___CPPdebugHook`; string "Borland C++ - Copyright 1999 Inprise") with German VCL resources (`LT/scripts/pe_inspect_imdeditor.out`).
- File sizes: the exe is 768000 bytes, which is the "~750 KB" on Tech's page (OLD/allaway.txt:68). The rar is 294926 bytes, which matches the "288 KB" vsadnik listing (OLD/eg49483.txt:239). That settles the question in `ships/prior-art.md:39`: the 288 KB figure is the compressed archive.
- Reference types it can add (v3): `Biggun, Smallgun, Rockets, Turret, TurretGuns, Fire, Flare, HangarIn, HangarOut, TractorBeam, Module, Gunpoint, PortalIn, DOCKPOS, PREDOCKPOS, Hinge1_opened, Hinge2_opened` [Critic: the hinge names are written with an underscore, `strings_v3.txt:3263-3266`; `Hinge1opened` is the menu item name. IMDeditor writes `PortalIn`, vanilla uses `PORTALIN` (5 refs); whether the engine compares case-insensitively is UNVERIFIED]. v2 lacks `DOCKPOS`/`PREDOCKPOS` (`LT/scripts/strings_v2.txt` vs `strings_v3.txt`). Vanilla SW3 prefixes (`LT/scripts/vanilla_refs.out`): Flare 23503, Module 3386, Fire 1494, Turret 401, Biggun 282, TractorBeam 270, Rockets 228, Smallgun 202, Gunpoint 78, **GKGun 54**, TurretGuns 27, HangarIn 22, HangarOut 22, PREDOCKPOS 11, DOCKPOS 11, **TurretGK 10**, PORTALIN 5, plus single odd spellings. The two SW3-only types are exactly the ones forum users had to import via `.REF` (OLD/t13859.txt:1009-1011; OLD/t13859p2.txt:876-880).
- Limits: the load path reads the 48-byte GNFO block into `0x4a43ec` (`0x401836`). It then compares `num_gvtx` at `0x4a4414` with 100 (`0x401843`) and `num_gmat` at `0x4a4418` with 100 (`0x401959`), and the GREF count at `0x4a8918` with 1000 (`0x402545`). Against vanilla (`LT/scripts/imd_counts.out`): max submeshes 239 (`ModuleStation_vks.IMD`, the only file over 100), max materials 23, max refs 377 (`Alien_MS.IMD`). The forum error "# of maximal objects (100) exceeded" on OBJ import (OLD/t13859p2.txt:590) is the same check.
- Chunk handling: GNIN appears only in a `cmp` (`0x4021ee`), never in a `mov` that builds a tag. GBND and GELP appear in both. ~~So IMDeditor reads GNIN and drops it on save~~ [Critic correction: the `mov` instructions for GBND/GELP/GREF (`0x40a3a2`, `0x40a4d8`, `0x40a5d4`) are in the code that runs after an OBJ import, not in the save path. Save writes the tag bytes that were read from the file, including GNIN when present (`0x403314`-`0x403378`, flag `0x4953fc` set at `0x4022e5`). The absence of a GNIN `mov` only means an OBJ import cannot create GNIN.] SW3's loader ignores GNIN (`ships/assets.md:97`).
- Known workflow fixes from the EG thread: one method fixes light shining through an imported model. Export OBJ with triangles, export `.REF`, re-import the OBJ, then "Import *.REF and REPLACE"; IMDeditor resets the materials to opaque (Protok St and Oxygenes, 2018-11-15, LT/dl/web/eg51964.txt:728-760). If that is not enough, mirror the model on X first (lightsss, :754-755). This points at the GMAT alpha fields (section 4). [Critic: UNVERIFIED. The post says the see-through value comes from the `.mtl` (:736), but IMDeditor's MTL writer has no `d`/`Tr` key, only `Ka`/`Kd`/`Ks` with four values, `Ns`, `illum` and `map_Kd ..\TEXTURE\%s` (`strings_v3.txt:96-100, 3820`). The mirror fix flips face winding, so back-face or normal direction may be the cause in some cases.]

## 4. Format notes extracted (GMAT)

krink's importer reads GMAT as: skip 4 bytes, `u32 name_len`, name, then 19 floats named `Shininess, ShinStr, Diffuse xyz, SelfIllum, Ambient xyz, Opacity, Specular xyz, OpacFalloff, Filter xyz, WireSize, IOR`, then `u32 TextureCount` and per texture `u32 type, u32 len, name, f32 amount` (`LT/docs/krink_imd_importer_2010.ms.txt`, `fn ReadGMAT`). `LT/scripts/gmat_fields.py` applies this layout to all 3664 vanilla GMATs, and every chunk ends exactly at its size (0 mismatches, `LT/scripts/gmat_fields.out`). The value distribution does not fit krink's names. It fits a D3D-style material (two leading zero words, four RGBA colours, one power value), which is how `mods/traffic/tools/imd/imdparse.py:7-9` reads it. [Critic: overstated. krink's names are the same as SW3SE's `imd_format.ksy` (`ships/assets.md:70-73`), and the one field that varies like a transparency value is float 9, which krink and SW3SE both call Opacity; SW3SE writes Blender's Alpha there (`.work/ships/dl/sw3se/imd_exporter.py.txt:219, 232`). Both readings agree on where transparency sits; they differ only on the names of constant fields. Which reading the engine uses is UNVERIFIED. Supporting the four-component view: IMDeditor's MTL export writes `Ka`, `Kd`, `Ks` with four floats each (`strings_v3.txt:97-99`).]

| krink name | values in vanilla | reading |
|---|---|---|
| Shininess, ShinStr | always 0.0 | two flag words (imdparse `flags`) |
| Diffuse xyz + SelfIllum | 0.196 grey mostly, alpha always 1.0 | colour 0 RGBA |
| Ambient xyz + Opacity | 1.0 or 100.0 RGB; alpha 1.0 in 3590, 0.0 in 27, 0.02-0.99 in the rest | colour 1 RGBA. The alpha varies, so this is the likely transparency value (UNVERIFIED) |
| Specular xyz + OpacFalloff | 0.0 to 0.8; alpha always 1.0 | colour 2 RGBA |
| Filter xyz + WireSize | 0.0 RGB (3 files 1.0); alpha always 1.0 | colour 3 RGBA (emissive?) |
| IOR | 0, 9, 19, 24, 39, 49 | specular power |

This bears on the SW3SE note that material settings do not round-trip (`ships/prior-art.md:42`). The only per-material field that varies is the colour-1 alpha, and IMDeditor's OBJ import resets it (section 3.2).
